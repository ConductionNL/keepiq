# Changelog

All notable changes to Keepiq are recorded in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Keepiq uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). Each entry names the OpenSpec change it comes from.

## [Unreleased]

### Added

- AI assistants can read vault metadata through three MCP tools: `listEntries`, `expiryReport` and `rotationStatus`. The tools return names, addresses, types, folders and dates, never a password, login or other secret value. They act only for the signed-in user and change nothing. Every call is written to the audit log with the tool name and the number of results. The tools appear only when OpenRegister is installed. (hermiq-ai-tooling)
- A change to a shared secret's value, login or additional fields now reaches every copy in one request, `PUT /api/v1/secrets/{id}/share-save`: the editor's row, every recipient's copy and every partner share are saved together or not at all. A save made from an older version, or one that misses a recipient added in the meantime, is refused and nothing changes. Saves for more than 100 copies are sent in chunks and committed at once; the chunks wait in a new table and can be used for 30 minutes. Partner instances are told to pull only after the save is committed. The old `/sync` and `PUT /api/v1/federated-shares/{id}` routes keep working for older web-app tabs and API clients. `POST /api/v1/versions/{id}/restore` takes an optional `baseUpdatedAt` and answers 409 when the secret changed since, and suspending a partner share that is no longer active now answers 404. (sharing-atomic-share-save, #1254)

### Fixed

- A generated password now always holds every minimum and every kind of character that was chosen or that the organisation policy requires. When the minimum numbers and symbols left no room for the other chosen kinds, the length grew only to those two minimums, so the password missed some of the numbers, symbols or other kinds. The length now grows to the sum of the minimums, counting one for every other chosen kind, as in Bitwarden. A character put in for a minimum is now as likely at any position; the first positions held a little less of them. Minimums with a fraction count as the whole number below them. The mobile apps' generator does the same. (clients-extension-finish, #1133)
- In the web app and the mobile apps, a policy minimum length above 128 now counts as 128. Every password request failed with "Length must not exceed 128 characters", and passphrases grew past 200 characters. (client-side-key-generator, #1220)
- Passphrases no longer use the four hyphenated words of the EFF list (`drop-down`, `felt-tip`, `t-shirt`, `yo-yo`), so a passphrase with hyphens always splits back into the same words. Five words still give about 64 bits. (client-side-key-generator, #1220)
- A member of a group a secret is shared with can now change it for everyone it is shared with, as the owner and write-grade members can. Their change only reached their own copy, so the owner and the other recipients kept the old value. Membership is checked at every save, so a member who left the group can't save for everyone, even when their copy was not removed. A use-only group share doesn't give this right, and a recipient of a direct share can't change it until they join such a group; then the right comes at once, with nothing to approve, and the owner is told unless the recipient can change it for everyone as a delegate or through a team folder they can write in. A member's sync through `PUT /api/v1/secrets/{id}/sync` needs a base version and every copy once, may not clear a copy's key and is checked again just before it writes, as a share-save is; otherwise it answers 409, or 403 when the source is a read-only copy from another organisation. (#1285)
- A save by a delegate, a team-folder writer or a group member through their copy now keeps the owner's previous value as a version of the owner's secret, so the owner can restore it. Only the writer's own copy kept a version, and a sync through `/sync` kept none at all. (#1285)
- Editing a shared secret in the web app updates the recipients' copies again. The copies were never updated, a write-grade member who changed only the password cleared the login and additional fields on the source, and a failed update showed as saved. A failed save now shows an error and changes nothing. (sharing-atomic-share-save, #1253)
- A recipient who may not write a shared secret can no longer change the value of their own copy, which split that copy from the source and every other copy. A copy shared directly, or through a group whose share is use-only or expired, or held as a team-folder Viewer, is view-only: the web app hides Edit, Restore and "Ask for new values" on it, keeps Save disabled in its edit dialog and says it is shared to view only, while moving, starring, archiving, tagging and deleting it still work. An offline edit of such a copy fails on replay with its values kept to copy or discard. `PUT /api/v1/secrets/{id}` and `POST /api/v1/versions/{id}/restore` refuse a change of the value, login or additional fields of a view-only copy with 428 `view_only`, and a change of only other fields, such as the folder, still saves. `PUT /api/v1/secrets/{id}/sync` refuses a received copy's id with 428 `forbidden`, since a sync starts from the source. Filling a secret request for a view-only copy is refused too; a refused fill, also one for a use-only copy or a read-only copy from another organisation, answers 428 instead of 500, stores nothing and leaves the request pending. (user-sharing, sharing-atomic-share-save, #1287)
- A save through `PUT /api/v1/secrets/{id}`, a sync through `PUT /api/v1/secrets/{id}/sync` and a version restore could overwrite a change that landed between their read and their write, such as a share-save from the web app while the browser extension saved. They now read and write in one step, so a change that lands meanwhile is kept in the version history instead of overwritten. A save or sync with a base version answers 409, as do a sync or restore without one; a save without one, filling a secret request for a user's secret and setting an expiry try once more on the current version, and answer 409 only if it moves again. (sharing-atomic-share-save)
- A delegate or write-grade member who saves a shared secret through their copy is now recorded in the audit log on the owner's secret too, with the holders that were left out. A restore made through a share-save is recorded as the version the client restored from. (sharing-atomic-share-save)
- Revoking a partner share while an update to that partner was still being sent could leave the partner's copy in place: the slower update replaced the pending unshare, so the unshare was never sent. An update now never replaces a pending unshare. (sharing-atomic-share-save)
- Suspending a partner share, also by saving without an unreachable partner or by removing the partner, now drops an update still waiting for its retry. The retry job kept contacting that partner and then showed the suspended share as failed. The retry job also checks each share again just before it sends, so only a send already under way can still arrive once. (sharing-atomic-share-save)
- When the partner deletes its copy of a share whose revocation is still waiting to reach it, or whose revocation was given up, the revocation is now complete and the share is removed. It used to keep waiting for an unshare the partner no longer needed, or stay behind as failed once the retries gave up. (sharing-atomic-share-save)
- A decline and a later accept from the partner no longer make a suspended partner share live again. Only the owner ends a suspension, by revoking the share or sharing again. The decline is still recorded in the owner's audit log. (sharing-atomic-share-save)
- Partner shares now pass to the new owner when a secret is handed over, through a delegation when the owner's account is deleted or through team offboarding. They stayed with the previous owner: the new owner could not revoke or suspend them, while after team offboarding the previous owner still could. The upgrade hands shares left behind this way to their secret's owner, and a partner share that isn't the secret owner's is no longer served. (sharing-atomic-share-save)
- Link shares now pass to the successor with the secret when team offboarding hands it over. They stayed with the leaving user: the successor could not see or revoke them, while the leaving user still could. Links a delegate created stay with that delegate. Keepiq keeps who made a handed-over link, so a compromise revoke of the leaving user still cuts it and one of the successor does not. The offboarding audit event counts the links handed over. The upgrade adds a column to the link shares and hands links left behind by an earlier offboarding to their secret's owner. Deleting an account still deletes the link shares it holds, also on secrets that pass to a delegate, and replaces the account as the maker of links someone else now holds with a marker that is not a valid Nextcloud user ID. The data export also lists the links a user made that were handed to someone else, flagged `handedOver`. (team-folder-sharing, gdpr-compliance, #1264)
- `keepiq ssh-agent` works as a systemd user service. Under systemd the agent moved to the background and left the unit, which systemd then stopped, so the agent never kept running. The new `--foreground` option keeps it in place, and the unit in `cli/README.md` now uses it.

### Removed

- The `vault_admin` group no longer counts as the People and offboarding admin area, and the General area no longer shows a notice about it. A member of that group who holds no delegation is now refused the admin handover and team offboarding. To keep those actions for them, delegate the People and offboarding area to their group on Nextcloud's administration privileges page before you upgrade. (admin-scoped-roles, #1043)

### Security

- The share write context, `GET /api/v1/secrets/{id}/write-context`, now answers only a user who owns the secret, is its delegate, holds a copy of it or can reach it through a team folder. Anyone else gets the same 404 as for an unknown id. A user who asks about a copy of their own whose share rows lead to no secret, for example because the copy has two share rows, gets an answer without a source, so they can still save their own copy, unless it is itself shared. Until now any signed-in user who knew a secret's id learned whether it existed, which secret it was a copy of and when that was last changed. (#1266)
- Sharing with another organisation verifies the partner's certificate chain more strictly. The chain must be exactly the partner's intermediate and its root. Every certificate above the recipient's must be a CA allowed to sign certificates, within its path length, and every certificate in the chain must be valid now. The owner's server refuses any other chain before it reaches the browser and says the certificate could not be verified. Upgrading every instance that shares with partners is what protects its users. New user and application certificates are marked CA:FALSE, and the root and intermediate carry their CA constraints whatever the server's OpenSSL configuration says. Some user certificates issued before are marked CA:TRUE; an upgraded instance never accepts them as an issuer, and such a certificate becomes CA:FALSE when re-issued. The web app no longer accepts one as the recipient's own certificate either: the next save of a secret shared with such a user suspends that partner share, and it stays suspended until the owner shares again, also after the certificate is re-issued. If an unusual OpenSSL configuration issued an instance's root without CA constraints, upgraded partners refuse its chain until that root is renewed, which changes the fingerprint the partners have pinned. (federated-sharing)
- The web app checks a partner recipient's certificate more strictly. It refuses a lookup answer for another cloud id than the one asked for, a self-issued intermediate, a recipient certificate marked as a CA, a recipient name that isn't a cloud id, and encodings it used to read leniently: a signature algorithm that differs from the one in the signed part, a signature with unused bits, more than one common name, one of an unexpected string type or one that isn't valid UTF-8, and RSA-PSS parameters that are incomplete, out of order or repeated, name a mask other than MGF1 or a trailer other than 1, or carry unknown fields. The case of a cloud id's path now counts, so a certificate for `bob@host/nc` no longer passes for a share with `bob@host/NC`. When saving a shared secret, a partner share refused this way is suspended, as one whose certificate no longer verifies. A failed partner lookup now suspends a share only when its reason comes with its own status, so an error page from a proxy no longer suspends shares for good. (federated-sharing, #1257)
- Sharing with someone at another organisation and enrolling in account recovery now encrypt to the public key of the certificate the browser verified. The browser accepts a certificate or key only as exactly one PEM block with nothing but whitespace around it and nothing after its encoded value, and refuses anything else. (federated-sharing, organisation-account-recovery)
- Keepiq records its decision not to take part in OpenRegister integration leaves: secret material and vault structure stay inside the vault's own access rules. A test now fails when a register schema declares `linkedTypes` or `mailObjectTemplate`, so the boundary cannot be crossed by accident. (leaf-integrations)
